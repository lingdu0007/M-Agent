# 模型契约由 Core 冻结且路由只发生在 Run 前

Runtime Core 定义 Model Contract 与 Model Requirements：Adapter 明确提供可静态校验的类型化 Model Capabilities、定量 Model Limits、Model Input Sizer 标识和稳定指纹，能力声明必须区分 streaming、tool calling、原生 structured output 与 usage reporting 的具体模式及可用组合，未声明组合默认不支持；Agent Definition 只声明正确运行所需的最低能力、容量与输出要求，prompt 约束 JSON、解析重试或 Output Repair 不能伪装成原生 structured output。“长上下文”以容量表达，“可靠 JSON”、工具成功率、延迟和成本属于 Eval 或运行观测产生的 Model Evidence，而不是 Adapter 自我声明的硬能力。Model Contract 记录稳定 `contract_id + version`、非敏感模型或 deployment 身份、能力/限制/Sizer/序列化模式指纹及 `PINNED` 或 `PROVIDER_ALIAS` 修订稳定性；Core 保证恢复时契约身份一致，但不虚假承诺远端 alias 权重不漂移，供应商返回的实际 revision 只作为 Run 事实记录。Definition Registry 在注册时离线校验完整契约，Context Budget 对冻结限制和 Sizer 校验每次完整请求，Model Step dispatch 只复核 Snapshot 一致性及本次请求能力，响应归一化显式暴露 Adapter 违约，Eval 只衡量经验质量。

Usage reporting 不是单一布尔值：Model Contract 对 input、output、cached input、reasoning token 等字段分别声明 `REQUIRED`、`OPTIONAL` 或 `UNSUPPORTED`，保留供应商原始单位与标准化映射来源；缺失 required 字段是 `MODEL_CONTRACT_VIOLATION`，optional 缺失记录 `UNAVAILABLE`，unsupported 禁止伪造。供应商拒绝已声明模式、返回无法归一化的协议包或未声明的 streaming/tool 组合也属于契约违约；已成功归一化但不满足业务 Output Contract 的内容属于 `OUTPUT_VALIDATION_FAILED` 并按冻结策略进入 Output Repair，除非具体 Contract 明确保证原生 strict schema 合规。Eval 分别报告协议违约率与业务输出合格率，不把两者折叠成一个“JSON 可靠性”。

Model Catalog、Model Router、Routing Policy、Model Fallback 和成本策略属于 Runtime Companion；Model Contract 属于具体 Adapter 实例与 model/deployment 配置，Adapter 类只能声明其协议能力上限，实例 Contract 必须取协议上限与目标配置的交集。官方 Catalog 可维护已验证条目，自定义 endpoint 由应用显式提供并承担声明准确性；注册和路由不通过真实请求自动探测。Catalog 的非敏感 deployment 属性可表达 provider、region、endpoint class 与数据保留声明版本，Routing Policy 以 Deployment Constraints 做硬匹配，但凭据、tenant ID、敏感 endpoint 和数据正文不进入 Catalog、Decision 或 Snapshot，合规结论只能引用外部版本化证据，属性未知或证据过期时硬约束 fail closed，Core 不参与凭据选择。

Router 只读取 Model Requirements、允许的 Agent Variant、版本化 policy、显式 Model Evidence，以及带来源时间和有效期的可用性快照，不读取原始 prompt、Conversation History 或敏感 Context Item。它在 `create_run` 前从已注册且满足需求的完整 Agent Variant 中完成选择，产出不可变 Routing Decision，记录最终 Definition 和 Model Contract 指纹、各候选结构化 reason code、确定性 tie-break，以及使用的 policy、evidence、Pricing Snapshot 和可用性快照版本与有效期；完整决策由 Companion Routing Store 持有，Core 只关联其标识和摘要。Routing Policy 不使用隐式加权总分：先以 capabilities/limits、Deployment Constraints、证据有效性和 hard Eval gate 过滤，再按声明了方向、缺失值策略及有效期的字典序目标排序，最终以稳定 `variant_id + version` 破除并列；随机分流、A/B 和按比例发布由应用先决定实验桶，再传入固定候选或 Policy。Model Fallback 也只能在 Run 创建前按冻结顺序选择下一 Variant。Runtime Core 随后冻结最终 Definition Snapshot，Runner 不选择模型或按价格路由；dispatch 后只可按冻结的 Retry Policy 重试同一 Model Contract，跨模型继续必须由应用显式创建并关联 Replacement Run，不能伪装成原 Run 的重试或恢复。

Router 返回结构化 Routing Result：成功为 `SELECTED`；无候选满足能力、Limits 或部署硬约束为 `NO_COMPATIBLE_VARIANT`；兼容候选均不满足硬价格、质量或稳定性门槛为 `POLICY_UNSATISFIED`；硬策略证据缺失或过期为 `EVIDENCE_UNAVAILABLE`；不可变 Catalog 身份或指纹冲突为 `CATALOG_CONFLICT`；规则不完整或不能形成确定顺序为 `INVALID_POLICY`。失败发生在任何 Session Claim 和 Agent Run 创建前，产生零模型 dispatch，应用只能补证据或显式选择另一已发布 Policy 后重新请求，Router 不偷换规则。

成本控制分为三个边界：Core 以 Context Budget、冻结的最大输出、Model Limits 和 Model Execution Budget 强制执行资源上限；其中 Execution Budget 同时限制整个 Run 及各 Model Binding 用途可 dispatch 的 Model Step Attempt 次数，每次外部调用前持久化原子预留，失败或结果不确定同样消费额度，恢复不返还，耗尽后以 `MODEL_EXECUTION_BUDGET_EXCEEDED` 确定性失败。Companion 依据版本化 Pricing Snapshot、最坏情况 token 估算和 Routing Policy 执行 Run 前候选过滤，硬成本策略在价格缺失或过期时 fail closed，软偏好只能产生显式 warning；账户、租户或周期额度的跨 Run 预占、并发结算和退款由应用或外部 Billing/Quota 服务拥有。实际费用以供应商 usage 和对应价格版本形成观测证据，usage 不可靠时只记录估算范围与证据缺口，不能伪造精确成本或在 Run 中途据此换模。

Agent Variant 冻结完整 Model Binding Set，按 `PRIMARY`、`CONTEXT_COMPRESSION`、`OUTPUT_REPAIR` 等用途分别绑定 Model Requirements、Model Contract、Sizer、Limits 和预算；专用 binding 缺失时只有显式引用 `PRIMARY` 才能复用，Runner 不在执行到某类 Step 时重新选模，LLM-as-judge 继续是隔离 Eval Run 的 Definition 而不进入 subject Run。Router 只消费应用或只读探针提供、带来源/范围/采样时间/有效期的 Availability Snapshot，不为一次路由隐藏发起模型请求；硬可用性策略遇过期快照 fail closed，软偏好可带 `STALE_AVAILABILITY` warning 继续，且两者都不触发 Run 内换模。Eval 可以从不可变 Report/Baseline 产生带适用目标、Variant、hard gate、质量/成本/延迟证据、置信度和有效期的 Model Recommendation，但 Recommendation 不自动更新 Catalog、Policy 或 Definition；Runtime Integrator 或应用发布流程必须显式批准为新 Routing Policy/Agent Variant 版本，垂直 Agent 即使跟随发布 channel，也只在 Run 创建前解析并把具体 policy 版本写入 Routing Decision，已有 Run 与 Session Turn 不变。

Model Limits 只包含影响单请求语义和预算计算的稳定边界；RPM、TPM、并发数、余额和周期配额属于动态 Operational Limits Snapshot，可供 Router 做 Run 前筛选但不冻结进模型语义，Core 不实现其全局计数器。dispatch 时发生限流仍是同一 Model Contract 下的 `TRANSIENT` Step Failure并受冻结 Retry Policy 约束，不能倒推为能力缺失或触发换模；需要跨 Run 预占的保证由外部调度或 Quota 服务拥有。

版本演进严格分层：模型或 deployment 身份、修订稳定性、序列化协议、能力模式/组合、稳定 Limits、Sizer 或结构化输出保证变化时新建 Model Contract 版本；Requirements、Binding Set、Execution Budget、Output Contract、Instruction 或绑定 Contract 变化时新建 Agent Definition/Variant 版本；候选 allowlist、Deployment Constraints、排序与成本门槛变化时只新建 Routing Policy 版本；价格、Availability、Operational Limits、Eval Report 和 Recommendation 更新只产生新快照或证据。所有版本不可覆盖，Catalog 精确引用版本；新快照可影响后续 Routing Decision，但不改变既有 Decision 或 Definition Snapshot。

当前无真实用户，因此 0.3 公共 API 重定时一次性以类型化 Model Contract/Requirements 替换 0.2 的四布尔能力契约，不长期维护自动兼容层；迁移 helper 只能生成最保守声明，无法推断的 Limits、Sizer、usage 字段和能力组合必须由集成者补全。0.3 后新增能力模式默认 unsupported，语义变化按上述规则升版；0.5 再交付 Catalog、Router 与 Eval Recommendation 闭环，不发生第二次模型 API 重置。

0.5 官方范围只提供版本化 Model Contract、Requirements、Binding Set、Catalog、Routing Policy/Decision、纯函数 capability/limits 匹配与结构化 reason code，以及在硬条件过滤后按显式优先级和稳定 tie-break 排序的确定性 Router；Pricing、Availability、Operational Limits 和 Eval Recommendation 只作为快照输入，并配套离线 fixture、契约测试及至少两个 Agent Variant 的参考比较。它不提供流量负载均衡、熔断、主动健康探测、bandit/ML 自适应路由、账户计费/额度预占、托管 Gateway/远程 Catalog 或 Policy 服务、Run 内自动换模及 Recommendation 自动采纳。该边界增加了显式契约与 Run 前配置步骤，也不提供单 Run 内的透明供应商故障切换，但避免供应商逻辑进入 Core、动态偏好污染 Agent 语义、恢复结果随路由漂移或 Eval 成为生产执行依赖。
